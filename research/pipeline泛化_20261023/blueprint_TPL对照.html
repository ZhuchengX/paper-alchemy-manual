TL;DR

要点

Team Paper Lite（下称 TPL）把「一个研究想法 → 一篇实证论文」做成了一条有闸门、能续跑、数字可追溯的流水线。我们要做的是它的镜像：「N 篇 autoresearch 论文 → 1 篇有含金量的 insight 论文」。TPL 的流程骨架值得整套借鉴；我们自己的长处在洞见来源，也就是巨人肩膀镜头：汪浩然的制度借鉴、ScholarCatalyst 的构思动作、凌杨的棋盘法。

  • 对照结果：TPL 的 16 个机制里，我们已有 5 个、做了一半的 6 个、完全没有的 5 个。差距最大的在终局成文（架构师三棱镜、全文数字机核、5 角色新眼审稿）和编排（一键续跑、统一的人工闸门）。
  • 和泛化方案的关系：泛化方案（packs）解决「能吃哪些领域的论文」，这份蓝图解决「每一轮怎么炼得更深、更可靠」。两件事互不阻塞，可以交替推进。
  • 落地：按 R5 拆成小任务 B0–B8，一次只落一个，每个都配验收。

user 标红的两条核心（2026-10-23）

① 输入侧足够宽：让有信息量的想法尽量都冒出来。TPL 什么都能吃，从一句话想法到完整研究方案都行。方案写得越完整，它越按你写明的方向去实施；写得越模糊，它越去探索更多候选。路线数也跟着变：详细方案 3 条，中等 4–5 条，模糊 6 条（说明书「输入侧足够宽」）。对到我们：现在 config/menu.md 只有一种写法，提议角度固定为 R1–R4（angles.json）。要改成按菜单写得多细来决定提议路数：只给主题就多开角度去探索，给了假设和坐标轴就收拢到这几个方向。见下表第 0 行。

② 中间侧足够深：想法定了以后，让它的贡献尽量做大。TPL 先拟 3–6 条平行候选，全部跑完，挑最强的一条；再给这条准备约 7 张扩展卡（稳健性 / 异质 / 机制 / 描述），最后才动笔（说明书「中间侧足够深」）。对到我们：下表第 3–5 行，小任务 B2（逐候选质检、选冠军）和 B6（冠军 G 的扩展牌组）。

只借思路，不碰代码

TPL 是商业闭源软件，使用承诺写明「不得二次开发 / 改编 / 反编译」。我们只借它公开说明书里写明的设计思想，下文每条都标了说明书的章节，不接触、不复刻它的代码和提示词。

1. 大白话：两家工厂

  • TPL 是一家「从种子到果树」的苗圃：你给一颗种子（研究想法 + 数据），它先把要种什么钉死（锚），同时育 3–6 棵苗（候选发现）让它们互相比，挑最壮的那棵；再给它嫁接 7 根枝（稳健性、机制……）；最后修剪、拍照、出图册（论文 PDF + 复现包）。每一步都有质检员，关键节点停下来问你。
  • 我们是一家「从矿石到金条」的炼金坊：输入是一大堆矿石（autoresearch 论文，真假混杂），要先验矿（筛出 solid 的），再碎矿（抽取成带条件的事实），然后用不同的炉子去炼。炉子就是巨人肩膀镜头：有的照中国社会制度去找答案（汪浩然），有的照「作者当年怎么被前人启发」去找（ScholarCatalyst），有的把矿摆进棋盘找空格（凌杨）。炼出几块候选金子后互相比，挑真金，再反复敲打验证，最后铸成一块有成色证书的金条（金子论文 + 证据包）。

两家的车间流程几乎同构：锚 → 地基 → 多条候选并行竞争 → 独立质检 → 选冠军 → 围绕冠军加深 → 终局成文 → 人工闸门。区别只在输入（一份数据 vs 一堆论文）和洞见来源（回归 vs 巨人镜头）。

2. 逐项对照：TPL 的机制 vs 我们现在

来源一栏：TPL 写说明书里的章节名；我们写 file 或 file:line。✅ = 已有，🟡 = 有一半，❌ = 没有。

3. 我们独有、TPL 没有的：巨人镜头层

TPL 的洞见来源基本只有「回归跑出来是什么」。我们的输入是一堆论文，洞见要从别处借来的眼光里来。这正是你说的「中间过程需要非常多巨人肩膀」。建议把它们统一成一个可插拔的镜头注册表：每个镜头是一个模板，输入统一（db + 棋盘 + G 草稿），输出统一（候选卡，带出处和信心来源），所有镜头的卡走同一条质检流程。

镜头它问什么现在在哪
汪浩然 · 制度借鉴人类社会、中国古代制度是怎么解决同一个协作问题的？（如科举的锁院回避、御史监察）pipeline/templates/10_institution_catalyst.md；case 在 run3 synthesis/institution_run/
汪浩然 · 升维升维看问题、低维出工具（P31）15_problem_lift.md
ScholarCatalyst · 构思动作作者当年从哪篇前作拿了什么、挪到了哪里？（M2 换挂点、M4 现象升格……）14_catalyst_ideation.md + skill catalyst-ideation
凌杨 · 棋盘法研究问题 × 方法族的棋盘上，哪些格子是空的、薄的、互相矛盾的？scripts/chessboard*.py，docs/10
统计 · 荟萃 / 发表偏倚效应在独立组之间稳不稳？作者自报和他人重跑差多少？scripts/meta_analysis.py、pubbias_regression.py
（可加）TPL · 三棱镜新在哪 / 故事是否自洽 / 为什么有人在乎见 B5

以后再找到新的巨人，比如你提到的「去中国社会制度找答案」的其他思路，就只需写一个镜头模板登记进去，不用动流水线。

4. 输入侧：怎么把 autoresearch 论文筛成 solid

TPL 的输入是用户给的可信数据，它只需判「能不能检验」（可行性闸）。我们的输入是 AI 生成的论文，真假混杂，难度更高。现有手段和建议补的：

  • 已有：筛选打 solid_score、看会议档次与机构（01b_triage.md、01c_affiliation.md）；独立来源组，防同一作者群刷屏（independence_graph.py）；发表偏倚回归。
  • 可以直接用的新信号：这次重抽里，抽取 agent 已经在逐篇记录「论文内部数字对不上」，例如 FORD 同一格在 Table 2 与 Table 7 写成 83.74 / 84.74，LEVER 的 Table 6 与 Table 8 也不一致。把它们汇总成每篇一个内部一致性分，进 solid 判定。
  • RUNBOOK 自己承认的缺口：autoresearch 论文要加强「去重去污」，即思想重复、幻觉引用、互相引用（RUNBOOK §3）。
  • 建议：每篇论文出一张「验矿卡」（代码 / 日志是否公开、内部一致性、是否可从公开日志复算、引用是否真实、与已有论文的思想重复度），作为 TPL「可行性闸」在我们这边的对应物。

5. TPL 具体在哪：五个细节习惯

TPL 之所以显得针对性强，不只是阶段多，而是每一步都写死了可核对的细节。这五个习惯我们目前大多只做到一半：

习惯TPL 的写法（说明书原样）我们现在
每阶段都有具名产物文件Stage 8 → findings_decision.md（含 STAR_ROUTE 编号）；Stage 13 → number_check_report.mdRUNBOOK 阶段表有模板和闸门，但不少阶段的产物文件名只写在模板正文里，没有一张总表
判决是封闭枚举VALIDATED / REVISE / DROP；PASS / PASS_DESCRIPTIVE_ONLY / KILL；full_paper / short_note闸门只有 PASS / FAIL，审查结论是自由文本
数量和回环都有上界3–6 条路线（按方案详略分 3 / 4–5 / 6）、约 7 张扩展卡、正文 6000–10000 词、≥3 表 + ≥3 图、审计 FAIL 最多重跑 2 次部分有：每个 agent 抽 4–5 篇、终稿 G 最多 6 条（MAX_FINAL=6）；回环没有上界
每个失败都有名字和修法「常见问题」表：报错原文 → 原因 → 一行修法经验散落在台账 docs/09_* 和 memory 里，没有给跑的人看的一张排障表
给人看的决策点只问一件事计划闸只看卡片标题 + 一两行，回车放行；结果闸只决定继续 / 改选 / 返回F6 勾选页做到了；其他人审点要读整份 md 才能判断

所以新增 B0：阶段契约表，排在所有任务之前。它也是 B7 编排器的直接输入。

6. 小任务清单（按价值 / 成本排序，一次落一个）

B0

阶段契约表：每阶段一行，全部写死

新文件 pipeline/STAGES.yaml（RUNBOOK 同步生成一张表）。每个阶段一行，写明：输入文件、产物文件名、判决枚举、机器闸门条件、数量上下界、回环上界、人工闸要回答的那一个问题、常见失败及修法。

验收：脚本校验 run3 的实际文件与契约逐项吻合，列出所有不吻合项；不吻合的要么改契约，要么记入台账。

B1

验矿卡：内部一致性分 + 验矿闸

从抽取的 extractor_notes 和 extraction_confidence 汇总出每篇论文的内部矛盾数，加上代码公开、引用真实性，写成 triage/solidity.csv；建库时允许按它过滤。

验收：在已抽的 50 篇上跑通，FORD、LEVER 这类被标出矛盾的论文分数下降；run3 默认口径的库逐字节不变。

B2

每个候选一个独立质检员，三态判决

04_review 拆成「逐候选 critic（VALIDATED / REVISE / DROP）+ 一个 judge 选冠军」，REVISE 最多打回提议者重炼 2 次。

验收：在 run3 的候选上重跑，每个候选都有一份 critique 文件；DROP 的不进终稿；与原 G1–G10 的差异逐条列表交你看。

B3

全文数字机核

新脚本把金子论文里每个数字对到 final_scores*.json / db 的出处，对不上就 FAIL（可设容差）。

验收：在 v3.6 正文上跑，输出逐数字对照表；故意改一个数，闸门判 FAIL。

B4

成稿的 5 角色新眼审稿

新模板：方法学家、领域专家、怀疑者、实践者、写作编辑，五人只读成稿和语料，不读 synthesis 与作者侧材料；修订后再终审。

验收：v3.6 拿到 5 份意见，每条意见指到段落；修订稿 diff 只动被指出的段落。

B5

架构师三棱镜 + 禁说清单

成文前，novelty / narrative / impact 三个 agent 各出一份论文骨架，decider 选一份；同时生成 claim_calibration.md，即允许 / 禁止的论断清单，交给写作 agent。

验收：三份骨架并排给你选；写作稿里不出现清单禁止的说法（脚本检查）。

B6

KILL 出口 + 每个 G 的扩展牌组

可行性闸：语料撑不起通解时，输出 null memo，诚实地写「这一轮不出金子，原因是……」。冠军 G 默认配一副扩展牌组：留一组覆盖率、按格异质、机制、反例、发表偏倚、成本口径、闭卷对照，由你砍。

验收：用一个故意很小的语料触发 KILL；run3 的 G4 自动生成 7 张卡。

B7

编排器：state + 续跑 + 统一闸门

pipeline/orchestrate.py：读 RUNBOOK 阶段表，写 state.yaml，按阶段渲染提示词、等闸门；interactive 模式在 5 个闸停下，auto 模式直接放行；用文件指纹跳过没变的阶段。

验收：--fake-agent 模式在一个 3 篇的小语料上从头跑到成文，中途 kill 掉进程，再续跑能接上。

B8

交付包 + 摘要回写

最后一步打包：论文 PDF、证据包（db 子集、打分脚本、逐数字对照表）、最终报告。摘要由没参与写作的 reader 重写，且不含具体数字。

验收：解压交付包，在一台干净机器上能复算出正文全部数字。

B9

输入侧足够宽（2026-10-23 user 定：立，排在 B1 之后）

菜单分详略三档：一句话想法 / 中等 / 完整方案。越完整越偏实施、越模糊越偏探索；提议路数随档位变（对照 TPL：3 / 4–5 / 6 条），不再固定 R1–R4（pipeline/angles.json）。哪一档都要先收敛成菜单里的一句「中心问题」（外行一分钟听懂、说得出什么算答上），再进提议：越模糊越要探索，但不能没有中心（凌杨 §3.7 书 p55、§4.2a 书 p65；config/menu.md「Central question」）。

启发池的巨人肩膀：除 ScholarCatalyst 外，凌杨也给了两条做法：第二轮检索用已纳入论文摘要里的同义词重搜，并追高被引论文的 cited-by，免得漏掉近邻工作（§3.2 书 p41）；跨学科合作、到陌生领域找灵感（§4.7 书 p91–93）。前一条已写进 01_purchase.md，后一条和启发池同向。
