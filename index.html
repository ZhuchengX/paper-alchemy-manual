PAPER ALCHEMY · 用户使用说明书

把一大堆 autoresearch 论文，炼成一篇值得精读的 insight 论文

章节照 Team Paper Lite 公开说明书一一对应，内容全是本仓库的真实流程。各模块做到哪了看 进度表；每个模块的完整机制看 设计细节。

这是什么一句话讲清

论文炼金 = 文献采购员 ＋ 证据抽取员 ＋ 统计审查员 ＋ 写作伙伴，跑在你本机。你的工作不是读完几百篇论文，而是定选题、在闸口拍板、判断最后那篇是不是真金。

目标是注意力经济：N 篇论文 → m 篇必读（m 远小于 N）。输出是抽象出通解的论文，不是摘要或综述。

① 输入侧：先验矿

一批论文，人写的或 autoresearch 产出的都行。摘要初筛、按机构二筛、按共享作者分独立来源组；另建启发池，找领域外的启发。

② 中间侧：多炉并炼

每篇拆成「带条件的事实 ＋ 算子程序」。多个提议者并行出候选通解，互不读对方；审查和打分另请人做。

③ 控制权在你

7 个闸停下等你，每个只问一个问题。agent 只提议，不拍板；花钱前先看配置卡。

④ 产出侧：成色可查

中英文金子论文 PDF ＋ 决策指南 ＋ 交付包。正文每个数字都能在包里复算。

这不是什么：不是一键出论文的 SaaS，不是帮你想题目的聊天框，也不是综述生成器。它是一条本机流水线：Claude Code 调度，codex（gpt-6-astra）跑 LLM 阶段，Python 脚本和闸门把关。

跑第一轮动手

每一轮一个独立的运行目录。agent 只能读这个目录和全文目录，读不到别的轮次的结论和答案。

① 写菜单、建运行目录

照 config/menu.md 写菜单：选题、中心问题、读者与注意力预算、时间窗、纳入 / 排除、锁定答案的论文编号（写在 “reserved for evaluation” 后面）。然后：

python3 -I pipeline/init_run.py ~/runs/run4 --run-id run4_xxx --menu ~/runs/menu_run4.md \
    --split 2025-07-01 --forbid ~/HITSZ/paper_alchemy_run3
  • 脚本和 schema 拷进运行目录，成为这一轮的冻结快照；占位符写进 run.json。
  • --forbid 列出 agent 不许读的目录；pipeline 目录总在禁读名单里。
  • 答案文件放在运行目录之外，只有最后的评估 agent 能读。

三类输入怎么填 · 带范例

① 选题与读者（必填）

选题：多次便宜调用 vs 一次贵调用——多 agent、并行采样、投票 / 聚合、辩论、自适应停止、test-time scaling。
中心问题：多花便宜模型的 token（多采样、多 agent、辩论、验证、共享、聪明地停），什么时候能追平或超过一次贵模型调用，要花多少真钱？
读者：做 agent 系统的研究者；注意力预算：一篇 ≤ 4,500 词的正文。
时间窗：2023-01-01 .. 2026-10-19

中心问题要外行一分钟能听懂，并说清什么算答上了；审查用它判终稿有没有跑题。

② 纳入 / 排除（必填）

纳入：train-free；报告了算力或成本；有受控基线。
排除：只训练策略的论文、单链推理、综述、没有任务准确率的。

③ 锁定答案（必填）

挑几篇「人类后来公认的结论」论文写进 reserved for evaluation。它们不进语料、不让任何 agent 读到，最后用来检验金子论文有没有独立炼出同样的结论。

另有 启发池（不用你填）：流水线按中心问题，用 13 个构思动作找领域外的启发论文并出 idea 草稿，只给提议者当镜头，不进统计。跑完看 inspire/INDEX.md。细节 →

③ 跟跑 · 离开 · 回来取成果

  • 中途离开：直接走。回来再跑同一条 orchestrate.py run，做完的跳过，断掉的重跑。
  • 进度：orchestrate.py status；各站进出多少篇看 traces/funnel.md（scripts/funnel.py 生成）。
  • 取成果：进 RUN_DIR/paper/。英文全文 PDF、中文正文 PDF、决策指南、changelog.md；交付包在 deliver/。

它怎么思考读懂流水线

一条固定的多阶段流水线，6 个模块：下锚 → 证据地基 → 候选通解轮 → 试味与扩展 → 终局成文 → 构思与评估。

核心 idea ① · 先拆后聚

剔除包装 → 带条件的事实 ＋ 方法程序 → 积木库 → 在积木层面找通解。每个方法写成算子程序，例如自一致性 k=9 写成 Gen(9,cot,same); Agg(vote)。

设计原则第 3 条；config/schema.md 算子表

核心 idea ② · 多炉并炼，裁判另请

多个提议者从不同角度并行出候选通解，互不读对方文件。每个候选单独派一个 critic，判 VALIDATED / REVISE / DROP；REVISE 最多改写 2 轮；judge 只从 VALIDATED 里选终稿，被淘汰的进 dropped_routes.md。另有巨人镜头出候选卡：制度借鉴、构思动作、棋盘法。

打分用 MDL：通解要短、解释事实要短、对更晚的论文有预测力（设计原则第 4 条）· B2 细节 · 巨人镜头

核心 idea ③ · 每条结论都要被反复敲打

按算力归一化比较，再做留一组稳健性、独立组荟萃、发表偏倚、矛盾对、闭卷对照。成文前先判这一轮撑不撑得起：撑不起判 KILL，写一页说明、不成文；撑得起就给每条结论发 7 张扩展卡，你砍卡。有争议的只写带边界的条件陈述。

设计原则第 6、7 条 · B6 细节

核心 idea ④ · 终局成文也被机器管住

三个架构师各出一份论文骨架，你选一份 → 按骨架写 → 脚本逐条核对禁说清单 → 正文每个数字核对来源 → 五个角色只读成稿做新眼审稿 → 翻译、出 PDF → 打成交付包，在干净沙箱里复算全部数字。

模块 1 · 下锚　定选题、中心问题、时间窗和锁定答案，跑起来后不再改（3 个阶段）

模块 6 · 构思与评估　用巨人镜头出新设想卡，查重、勾选花钱；最后对照锁定答案评估（8 个阶段）

几个常见疑问

问题答
G1、G4 是什么？金子论文里的第 1、第 4 条通解。每条在 final_candidates.json 里有层级、可执行检验和支撑行。
为什么有好几个 db 目录？同一份抽取在不同口径下各建一库。原 db/ 永远不动，旧版论文的数字随时能复现。
被淘汰的候选还在吗？在。全部保留；删掉的卡移到 _archive/，只归档不删除。
某个数字从哪来？正文数字 → final_scores*.json → 支撑行 → db/results.csv → extract/<id>.json 的表号。数字机核逐条核对，每个数字在 number_check/registry.jsonl 里有一行来源指针。
